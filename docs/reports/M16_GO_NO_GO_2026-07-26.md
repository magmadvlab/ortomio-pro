# M16 - Verbale go/no-go release commerciale 1.0

## Decisione

**NO-GO alla certificazione commerciale 1.0 — 26/07/2026.**

Il repository dispone di una baseline locale compilabile e delle implementazioni M15, ma non esistono ancora evidenze remote sufficienti per affermare `deployReady=true`. Il deploy fisico Vercel di `main` non sostituisce migrazioni applicate, isolamento tenant, restore drill, provider reali, pilot e validazione agronomica.

## Evidenze locali raccolte

- type-check verde;
- 30/30 test cumulativi M15/O05 verdi;
- build Next.js verde con 153 pagine;
- audit release debt verde: 98 marker classificati, zero non classificati e zero M15;
- migrazioni O38-O43 presenti nel repository;
- O40 consolidato sull'unica versione PRO;
- O45 limitato agli 8 file con zero importer e sostituti vivi verificati;
- PR #53, #54, #55, #56 e #58 confluite; #57 chiusa come duplicato senza diff;
- #59 (riconciliazione M15/O05) e #60 (O45) ancora nella catena di review al momento del verbale.

Queste evidenze provano `localReady`; non provano la readiness remota.

Lo screenshot Supabase/Vercel del 26/07 mostra i deploy Preview pronti ma il controllo **Supabase Preview skipped**. Questo prova la compilazione del codice preview, non l'applicazione delle migrazioni al database.

## Correzione del gate automatico

`/api/admin/release-readiness` ora verifica anche:

- colonne delivery degli inviti;
- account commerciali, fatture e audit;
- sospensioni e grant assistenza;
- evidenza history migrazioni;
- isolamento tenant;
- lifecycle commerciale E2E;
- periodo shadow e revisione agronomica.

Gli identificatori esterni obbligatori aggiunti sono:

- `RELEASE_MIGRATION_AUDIT_ID`;
- `RELEASE_TENANT_ISOLATION_RUN_ID`;
- `RELEASE_COMMERCIAL_LIFECYCLE_E2E_ID`;
- `RELEASE_AGRONOMIC_SHADOW_ID`;
- `RELEASE_AGRONOMIC_REVIEW_ID`.

Restano inoltre obbligatori snapshot, restore drill, Security Advisor, provider smoke e pilot gia' presenti nel gate.

## Condizione per il prossimo GO

Il verbale puo' diventare **GO** soltanto quando:

1. tutte le PR della baseline sono confluite in `main`;
2. lo staging isolato esiste con snapshot e rollback identificati;
3. tutte le migrazioni risultano applicate nella history riconciliata;
4. i test remoti O01-O43 producono gli identificatori di evidenza previsti;
5. `/api/admin/release-readiness` restituisce `schemaReady=true`, `externalReady=true`, nessuna violazione/errore e `deployReady=true`;
6. il controllo remoto `npm run release:check:remote` termina verde.

Il probe schema puo' essere rieseguito con `npm run release:check:commercial-schema`; termina con codice non-zero finche' le relazioni o colonne richieste sono assenti.

Fino ad allora il prodotto puo' avere deploy tecnici in Production, ma non e' certificato come release commerciale 1.0.
